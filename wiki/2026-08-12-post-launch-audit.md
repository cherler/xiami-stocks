# 虾米看股上线后审查报告

审查日期：2026-08-12

审查范围：`xiamimate-stock-lab` 当前代码、部署样板、主站挂载形态与本地集成验证。

审查原则：研究工具不替用户作出投资决定，但必须保证研究记录不串户、数据状态不被误读、关键操作可恢复。

## 一页结论

项目的研究流程、真实数据接入、数据状态提示和测试基础已经超过普通原型：后端完整测试已通过，前端检查、测试和构建也全部通过。上线后最需要优先处理的不是再加功能，而是把**导出可用性、用户隔离、后台任务可靠性、计费失效策略**补成生产级闭环。

本次确认了 2 个可直接影响线上用户的高优先级问题，另有 4 个在多用户/持续运营时风险很高的问题。最紧急的是：两个“导出”按钮没有走线上专用 API 前缀，当前主站入口下会直接 404。

| 优先级 | 数量 | 含义 | 建议时限 |
| --- | ---: | --- | --- |
| P0 | 2 | 数据隔离或关键恢复能力可能失效 | 24 小时内处理 / 验证 |
| P1 | 4 | 成本、任务或主机权限会在运营中造成明显损失 | 1 周内排期 |
| P2 | 5 | 性能、稳定性、可观测性和发布质量风险 | 2–4 周内处理 |
| P3 | 3 | 可维护性、体验一致性与长期回归风险 | 持续治理 |

## 1. 主站路由与关键功能审查

### P0-01：两个导出入口在主站挂载路径下失效【已复现】

**证据**

- `apps/web/src/config.ts:15-26` 已定义线上 API 前缀：页面挂在 `/stocks/` 时，接口必须访问 `/stocks-api/api/v1/...`。
- 但 `apps/web/src/App.tsx:1112` 的“导出研究池”和 `apps/web/src/App.tsx:4704` 的“导出 JSON”写死为 `/api/v1/...`。
- 使用当前主站入口验证：`/api/v1/companies/export`、`/api/v1/export` 均返回 404；相同接口经 `/stocks-api/api/v1/...` 均返回 200。

**影响**

研究池导出、用户手写记录备份导出是恢复与迁移能力的一部分。按钮存在但下载失败，会让用户在需要备份时失去可用退路。

**优化方案**

1. 两个静态下载链接统一由 `apiUrl("/api/v1/...")` 生成，禁止手写根路径 `/api`。
2. 在现有 API 基址测试中补充 `<a href>` 的断言，而不是只测试 `fetch`。
3. 在发布前的网关冒烟测试中，以 `/stocks/` 入口点击两种导出，校验 HTTP 200、下载文件名和内容类型。

**验收标准**

- 用户从 `https://<域名>/stocks/` 点击两个导出按钮，都得到文件下载而不是主站 404 页面。
- 新增自动化测试能够阻止未来再次写入裸 `/api/v1/...` 下载链接。

## 2. 身份、权限与数据隔离审查

### P0-02：多用户模式下 RLS 失效只记录警告，服务仍继续运行【上线核验】

**证据**

- `apps/api/stock_decision/pgbackend.py:699-725` 已能正确识别数据库角色是否是超级用户、是否绕过 RLS、受保护表是否不足。
- `apps/api/stock_decision/main.py:301-338` 在多用户模式中仅打印警告，并不会拒绝启动。
- `apps/api/stock_decision/access.py:159-171` 显示接入主站后默认会进入 `multi` 模式；这是公开用户使用时最敏感的路径。

**影响**

当生产数据库连接角色意外带有 `SUPERUSER` 或 `BYPASSRLS`，或新表没有纳入 RLS 时，任何遗漏用户域过滤的查询都可能静默读到别人的研究记录。系统当前能“提示”，但不能“阻止错误上线”。

**优化方案**

1. 在生产 `multi` 模式下改为**失败即停止启动**：RLS `effective=false` 时拒绝提供服务。
2. 仅允许显式开发开关（例如 `ALLOW_UNSAFE_RLS=1`）绕过，且禁止出现在生产环境变量中。
3. 将 `/health` 中的 RLS 状态接入监控，`row_level_security != 生效` 立即告警。
4. 发布前增加“双用户隔离测试”：用户 A 创建的公司、判断、任务、导出文件均不能被用户 B 读取或猜测。

**验收标准**

- 在预发布环境故意使用可绕过 RLS 的角色时，API 进程不能成功启动。
- 正常专用角色下，健康检查明确显示 RLS 生效。
- 两个真实登录用户的隔离回归测试通过。

### P1-01：身份 Cookie 被作为未限量的进程内缓存键【已确认】

**证据**

`apps/api/stock_decision/access.py:106-109、184-218` 用完整 Cookie 字符串作为 `_CACHE` 字典键；缓存只判断 60 秒过期，但不会删除过期键，也没有大小上限。

**影响**

- 恶意或异常客户端持续发送不同 Cookie，可让进程内存持续累积。
- 完整 Cookie 会在服务进程内存中保留，增加诊断转储、意外日志或内存读取时的敏感信息暴露面。
- 登录态/权限变更最多滞后 60 秒。

**优化方案**

1. 缓存键改为 Cookie 的 HMAC/SHA-256 摘要，内存中不保存原文 Cookie。
2. 使用有容量上限、自动淘汰过期项的 TTL/LRU 缓存；建议先限制在 5,000–10,000 条。
3. 在网关与 API 层限制 Cookie 头长度，拒绝异常请求。
4. 对登出、封禁或权限回收明确缓存失效策略；高风险操作可缩短缓存时间。

**验收标准**

- 压测不同 Cookie 后缓存大小有明确上限，内存不线性增长。
- 缓存内容中检索不到原始 Cookie。
- 被撤销用户在约定时限内无法继续访问。

## 3. 运行权限与主机安全审查

### P1-02：API systemd 服务默认以 root 运行【已确认】

**证据**

`deploy/systemd/xiamimate-stocks.service:9-35` 未声明 `User=` / `Group=`。systemd 默认以 root 运行；文件注释也明确当前没有单独服务账号。

**影响**

研究服务会处理外部数据源、文档、模型响应和上传内容。即使现有 `ProtectSystem`、`PrivateTmp`、`NoNewPrivileges` 已经是良好起点，一旦出现远程执行或依赖链漏洞，root 权限仍会显著扩大破坏范围。

**优化方案**

1. 创建专用低权限用户 `xiamimate-stocks`，仅拥有数据目录和必要缓存目录权限。
2. 用 `StateDirectory=` 或显式 `ReadWritePaths=` 限定唯一可写目录；数据目录与代码目录分离。
3. 增加 `UMask=0077`、`ProtectHome=true`、`PrivateDevices=true`、`CapabilityBoundingSet=` 等收紧项。
4. 在预发布环境先验证迁移、备份、导出和日志权限，再切换生产。

**验收标准**

- 生产进程非 root 运行。
- 服务仍可读配置、写研究数据、执行备份；其他系统目录不可写。

## 4. 后台任务、调度与计费审查

### P1-03：模型任务与同步调度仍依赖当前 API 进程【已确认】

**证据**

- `apps/api/stock_decision/background.py:19-20、104-145` 将执行句柄保存在进程内 `_RUNNING`，以 `asyncio.create_task` 运行。
- `background.py:148-159` 证明重启后只会把“排队中/运行中”标记为“已中断”，不会恢复执行。
- `deploy/systemd/xiamimate-stocks.service:27-31` 明确只能单 worker，并设置 `Restart=always`。
- `scheduler.py:693-711` 的调度循环也在 Web API 进程中；单次超时后，线程无法被 Python 强制终止，后续任务可能与未真正停止的外部调用重叠。

**影响**

切换部署、崩溃或重启时，长模型任务会中断；用户可能需要重新发起并再次消耗资源。单进程也是吞吐上限，用户增多后会出现排队不可解释、同步推迟或重复调用风险。

**优化方案**

1. 将 Web API、调度器、任务 Worker 分离；API 只创建持久任务，Worker 从 PostgreSQL 原子领取任务。
2. 任务表加入尝试次数、心跳、锁租约、幂等键、可重试/不可重试原因和取消状态。
3. 先实施过渡方案：发布前停止接收新长任务、优雅等待；任务重启后允许用户“重试上次任务”，且不会重复计费。
4. 对每种模型任务建立“请求已提交、执行中、成功、已中断、可重试”的统一前端状态。

**验收标准**

- 任务执行中重启 Web API，不会丢失已提交记录；恢复后有明确重试结果。
- Worker 可独立扩容，Web API 不因模型运行而阻塞。
- 同一目标的同类任务不会重复消费。

### P1-04：积分冻结服务故障时，AI 调用会继续但不计费【已确认】

**证据**

`apps/api/stock_decision/llm.py:304-352` 在积分服务不可达或返回 4xx（额度不足 402 除外）时返回非激活 Meter，后续模型调用继续执行。

**影响**

这是有意的“可用性优先”设计，但公开多用户环境中，积分服务故障可能让模型调用无成本持续发生，形成成本泄漏和滥用窗口。

**优化方案**

1. 区分部署模式：多用户生产默认 `fail-closed`，冻结失败时不调用模型并提示稍后重试；个人本地模式可保留 `fail-open`。
2. 若必须保留降级调用，设置总额/每用户/每小时的未计费熔断上限，并实时告警。
3. 对“本次未计费”提供管理员审计和用户可见的任务状态，避免误以为已正常结算。

**验收标准**

- 生产积分服务 5xx 时，不会无限触发模型请求。
- 降级策略、上限和告警由环境变量明确声明，并有自动化测试。

## 5. 数据正确性、时效与供应商可靠性审查

### P2-01：市场资金流接口是页面请求时实时拉取，冷启动时可直接 503【已确认】

**证据**

- `repository.py:6541-6545` 的市场资金流视图每次调用都依赖 `_fetch_market_fund_flow()`。
- `providers/stock_sdk.py:98-138` 只有 5 分钟进程内缓存；冷启动时会启动 Node 子进程访问上游，12 秒超时且无持久快照。
- `main.py:2149-2154` 无缓存数据且上游失败时直接返回 HTTP 503。

**影响**

驾驶舱最抓眼球的资金流图恰恰容易在刚发布、刚重启、上游波动时消失。用户会看到“数据不可用”，而不是带时间戳的最后已知数据，影响对产品稳定性的信任。

**优化方案**

1. 将资金流拉取放入定时同步任务，结果持久化为带 `as_of`、来源和状态的快照。
2. 页面优先读取最近成功快照；上游失败时仍显示旧数据及“截至时间/已过期”标识。
3. 设置数据新鲜度 SLO：例如交易日内超过 15 分钟未更新提示降级，超过 1 日不作为“实时”展示。
4. 将数据源失败写入统一健康状态和告警，而不是仅表现为页面错误。

**验收标准**

- 重启服务、断开 StockSDK 时，驾驶舱仍能展示最近有效快照和明确时间。
- 用户能区分“实时”“延迟”“不可用”，不会把旧数据当成当前数据。

### P2-02：双数据库发布一致性没有成为自动门禁【上线核验】

**证据**

项目已有 `check:backends` 和 PostgreSQL/SQLite 测试流程，但当前 GitHub 工作流仅允许手动启动（`.github/workflows/tests.yml:12-22`）。本机 PostgreSQL 对比服务未启动，35 个比对失败属于“环境未就绪”，不能据此认定一致性已通过。

**影响**

代码在 SQLite 下通过不代表 PostgreSQL、RLS、迁移与生产查询都安全；过去注释也记录过多次只在 PostgreSQL 发生的问题。

**优化方案**

1. 发布前必须运行 PostgreSQL 通道、迁移检查与双后端契约测试。
2. 将轻量检查放到每次合并请求，将完整双数据库套件放到发布候选或每日定时；避免“只有手动记得才会跑”。
3. 对迁移编写向前/向后兼容、备份、回滚演练清单。

**验收标准**

- 每个发布版本都有可追溯的 PostgreSQL 绿色记录。
- 线上数据库迁移前后均通过关键读写、导出与 RLS 冒烟测试。

## 6. 前端性能、稳定性与维护性审查

### P2-03：前端主包和图表包偏大，驾驶舱首访性能需要实测【已确认】

**证据**

本次构建成功，但 Vite 提示大 chunk：主包约 516 KB（gzip 153.6 KB），图表包约 641 KB（gzip 214.5 KB）。`apps/web/src/App.tsx` 约 6,999 行，`styles.css` 约 7,052 行，当前有 56 个 `useEffect`。

**影响**

桌面开发机不容易感觉到问题；在移动网络、低性能设备或首次进入“驾驶舱/公司档案”时，下载、解析和渲染图表可能拖慢可交互时间。单一超大入口也增加了 UI 改动的回归概率。

**优化方案**

1. 按“今天、找票、公司、我的判断、设置”做路由级懒加载；图表库只在需要图表的页面加载。
2. 按业务域拆分 `App.tsx` 和样式：布局、数据请求、驾驶舱、公司档案、找票、任务分别独立。
3. 建立性能预算和真实用户监测：初始 JS、LCP、INP、错误率按页面记录。

**验收标准**

- 驾驶舱以外的页面不下载图表包。
- 移动 4G 条件下核心页 p75 LCP < 2.5 秒、INP < 200ms（以真实数据为准）。

### P2-04：前端请求没有统一超时与取消机制【已确认】

**证据**

`apps/web/src/api.ts:154-167` 的统一 `apiFetch` 直接等待 `fetch`，没有 `AbortController` 或超时。部分同步接口会触发上游数据请求。

**影响**

网络半断、反向代理卡住或供应商慢响应时，按钮可能长时间处于等待状态，用户不知道是“还在运行”还是“已经失败”。

**优化方案**

1. 为读接口、普通写接口、后台任务提交接口分别设置合理超时和可取消策略。
2. 所有超时都提供“重试 / 查看数据状态”，而不是无期限转圈。
3. 长操作全面走后台任务；同步接口只做快速入队。

**验收标准**

- 人为延迟 API 后，页面能在约定时间内停止等待、保留输入并显示可操作的恢复入口。

## 7. 用户体验与无障碍审查

### P3-01：破坏性操作仍大量使用浏览器原生确认框【已确认】

**证据**

项目中至少 13 处 `window.confirm`，包括删除研究任务、投资逻辑、交易记录、策略、订阅源及数据库恢复（例如 `App.tsx:1072、3009、4243、4644、6641`）。

**影响**

原生确认框没有统一层级、上下文、焦点管理和撤销能力；不同浏览器与移动端表现不一致。对“删除任务”“恢复备份”这种不可逆或影响范围大的操作，用户难以在一瞬间判断后果。

**优化方案**

1. 使用统一确认弹窗：明确对象、影响范围、是否可恢复和确认按钮文案。
2. 对可恢复操作提供短时撤销；对数据库恢复、批量删除使用二次确认或输入名称确认。
3. 给弹窗实现键盘焦点锁定、Esc 行为和屏幕阅读器标签。

**验收标准**

- 所有删除/恢复操作使用一致组件；高风险操作的结果可在操作记录中追踪。

### P3-02：现有体验质量基础良好，但缺少真实用户体验监测【上线核验】

**正面观察**

四套主题的对比度检查已通过；界面中已存在较多 `aria` 文案、数据状态和错误信息的人类可读转换。这些是价值投资工具应继续保留的优点。

**缺口与方案**

还没有看到发布后的真实操作路径数据：用户最常在哪一步停下、模型任务是否等太久、资金流图是否经常缺数据、导出是否失败。建议仅采集匿名行为和性能事件，不采集投资逻辑正文或敏感研究内容。

建议指标：新建公司完成率、写判断完成率、导出成功率、后台任务中断率、页面 p75 加载时间、接口错误率。

## 8. 可观测性、告警与发布流程审查

### P2-05：已有健康状态，但没有完整的生产观测与告警闭环【已确认】

**正面观察**

系统已有数据同步状态、RLS 状态和任务运行记录；这是非常好的基础。

**缺口**

当前代码与部署样板中未发现统一的请求指标、异常追踪、任务成功率、模型成本异常或 RLS 健康告警。仅依赖日志会导致问题在用户反馈后才被发现。

**优化方案**

1. 建立统一请求 ID，贯穿浏览器、API、Worker、外部数据源调用。
2. 最低限度监控五类指标：HTTP p95/5xx、任务队列与中断率、数据源新鲜度、模型/积分错误率、RLS 是否生效。
3. 设定告警：RLS 失效、连续同步失败、数据过期、未计费 AI 调用、导出失败率突升。
4. 为告警写一页运行手册：谁处理、如何确认、如何临时降级、何时通知用户。

**验收标准**

- 故意制造一次数据源失败与一次 RLS 异常，负责人能在约定时间内收到告警并按手册定位。

### P3-03：依赖安全与发布门禁仍可加强【上线核验】

**证据**

前端生产依赖本次审计为 0 漏洞；但 Python 依赖尚未接入漏洞扫描。GitHub 工作流目前仅手动触发，发布是否经过完整测试依赖人工执行。

**优化方案**

1. 在发布流水线中固定运行 npm 与 Python 依赖漏洞扫描；npm 审计显式使用稳定官方源。
2. 为发布标签建立不可跳过的门禁：前端构建、后端测试、PostgreSQL/RLS 测试、网关冒烟、备份导出验证。
3. 每次部署记录版本号、迁移版本、配置变更和回滚路径。
