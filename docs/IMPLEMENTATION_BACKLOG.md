# 虾米看股：实施清单

| 项目 | 内容 |
|---|---|
| 代码名称 | `xiamimate-stock-lab` |
| 更新日期 | 2026-08-03 |
| 当前版本 | 0.21.0，阶段 1 开发中 |
| 使用边界 | 个人研究辅助；不自动交易、不荐股、不提供目标价或短线信号 |

## 1. 当前实际可用的能力

当前版本已经是一个**可保存个人研究记录的基础版**，但还不是完整的股票研究系统。

- 已接入 StockSDK 的真实 A 股行情：已关注公司的名称、价格、涨跌幅、PE、PB、52 周区间、市值（若来源返回）、同步时间和来源；可在总览手动刷新并保存快照。
- 已接入 StockSDK 前复权日线：公司档案展示 5/20 日、年初至今、近一年表现，走势图可切换近 3 月、近 6 月、近一年窗口（本地保留约 260 个交易日），并标明数据口径、截止日和来源。
- 行情走势图已加入事实型标注：区间高低点、区间均价、52 周高低参考线、MA20/MA60，以及把已记录事件按发生日标到价格曲线上；图下用一行说明窗口区间、区间涨跌、振幅、当前价在 52 周区间的位置和已标注事件数。标注只描述已同步的事实，不生成买卖信号。
- 已接入 AKShare / 新浪财经定期报告：公司档案可手动同步利润表、现金流量表和资产负债表，并展示营收、归母净利润、经营现金流、资产负债率和年报 ROE 估算趋势。
- 财务趋势图可切换“年度报告 / 全部报告期”口径：柱顶标注同比增速（去年同期为负或缺失时不显示），金额轴以 0 为基准并在亏损或现金流为负时向下延伸，混合口径下年报列会浅色标出；悬停可看净利率与经营现金流占净利润的比例。
- 已实现公司档案固定 URL，例如 `/companies/1`；档案页提供“复制档案链接”，刷新或直接粘贴链接都会回到同一家公司。
- 已接入公司简况：巨潮资讯的公司资料与公告披露、同花顺的分红方案、新浪的限售解禁安排。公司档案顶部新增“公司简况”区，分为操盘必读（股本结构、最近分红、股息率估算、股利支付率、上市与发行、下一件已排期的事）、公司概况（主营业务、行业、法人、注册资金、成立与上市日期、地址、经营范围、机构简介）和大事提醒（分红、解禁与公告的时间线，公告可点开原文）。某个子接口取不到时会显式列出缺口，不用占位内容冒充。
- 已实现持仓与交易决策账本：可建立组合、手工录入买卖流水，并要求写下当时的理由；持仓、移动加权成本、浮动与已实现盈亏、权重全部由流水推导，交易会留存下单当时的投资逻辑原文。公司档案新增“持仓与决策账本”区，总览的集中度在有交易后改按持仓市值计算。不连券商、不自动下单、不给买卖建议。
- 已实现研究任务：候选清单可一键存成研究任务，把"当初用的哪套条件、哪份数据（全市场样本量、命中数、财务报告期、行情截止日）"和每家的入选依据一起留档。任务里逐家推进（待看 / 已建档 / 已排除）并写下各自的结论，进度可见；结束时写一句整体结论。已经在研究池里的公司自动标为已建档，不必再走一遍。
- 已补上全市场的年初至今与近 60 日涨跌（东财快照一次带回），并开始自建全市场估值历史：每次同步底座会把当天的 PE/PB 落一条记录，累计满 250 个交易日后才给全市场分位，在此之前只显示当期值并说明还差多少——不用一天的样本冒充历史分位。
- 已实现市场云图：全 A 与四个主要指数可切换，按行业聚合成色块，点击行业下钻到行业内公司，点击公司建档或打开档案。指标可切净资产收益率、销售毛利率、营收同比、净利润同比、市盈率、市净率与当日涨跌；面积优先用总市值，行情源未提供市值时退回公司家数并在覆盖说明里标明。行业层用成员**中位数**而不是平均值，避免单只极端值（例如亏损公司的负值）主导整个行业。比率类指标用单色阶（深浅=数值高低，不暗示好坏），同比与涨跌用红涨绿跌的双向色阶。页面写明云图不排序推荐、不提供短线追涨入口。
- 已实现价值候选清单与策略库：不设任何条件也能出候选。首批四套可用的预置策略（低估防御型、质量稳健型、经营改善型、质量成长型）加一套待数据的（股息现金流型），每套写明出处与已知偏差，并声明依赖字段——字段完整度不足时该策略自动停用并说明缺什么。候选按"多策略交集优先"排序：被多套逻辑不同的策略同时选中的排在前面。每家可展开看到全部入选依据的实际值与报告期，可一键建档进研究池；任何一套策略都能复制成自己的（fork 会带上原策略的已知偏差）。每次运行都记录策略、条件、样本量与命中数，便于复现。候选页内可直接编辑条件：改门槛、加减条件、换排序后先"试跑（不保存）"，满意再存成自己的一套；每个可选字段都标出口径提示与底座完整度，数据不足的字段会提前提示而不是等到跑不动。
- 已建立全市场数据底座：覆盖全 A（约 5500 只）与沪深300、中证500、上证50、中证1000 四个主要指数的成分。每只股票存价格、涨跌幅、市盈率、市净率、总市值与流通市值，以及按报告期的营收与净利润及其同比、净资产收益率、销售毛利率、每股收益、每股净资产、每股经营现金流。行情主源为东方财富全市场快照，不可达时降级到新浪（只有价格），降级与缺失字段都会记录在快照日志里并在"数据状态"页显示字段完整度。作为每日调度任务运行。
- 已接入行业归属与同业对照：同步公司简况时会用巨潮的证监会行业分类回填档案里的"待补充"行业（不覆盖用户自己写的分类，并记录来源）。新增"行业对照"页，按行业分类把研究池里的公司放在一起比较最新价、PE(TTM) 与 PB 及各自的 5 年分位、年报 ROE、毛利率、净利率、现金含量、资产负债率与营收同比；公司档案的"行情与估值"标签里也有同一张对照表并高亮当前公司。页面明确标注两条边界：对照范围只是本地研究池而非全行业样本，行业口径为证监会分类且较粗；缺数据的格子显示"—"并说明原因，不用 0 顶替。
- 已完善研究池管理与档案分标签：公司档案页可按分组筛选、按分组/涨跌/名称/建档时间排序、逐家改分组、移出或放回研究池（软移除，档案与研究记录都保留），并支持批量按代码导入（逐个用行情校验，已存在的跳过）与研究池导出。公司档案拆成六个标签页——公司简况、行情与估值、财务、持仓与交易、逻辑与证据、事件记录——标签写进 URL（如 `/companies/1?tab=finance`），链接仍可直接分享到某个分区。
- 已补齐财务指标与异常提示：定期报告新增营业成本、研发费用、资本开支、应收、存货与有息负债等原始科目，并在本地计算毛利率、净利率、现金含量、自由现金流估算、有息负债率、研发费用率、应收与存货周转天数以及 TTM 营收与归母净利润。每个指标标明计算口径与所用报告期；非年报只与年报比较比率，金额与周转天数会写明"口径不可直接相比"；来源没有的科目保持为空而不是 0，并在提示区列出缺口与需要注意的地方（净利润为正但经营现金流为负、现金含量低于一半、应收增速明显快于营收、毛利率同比变动超过 5 个百分点）。
- 已实现复核工作台与判断归因：`/reviews` 会按"复核日期到期、关联交易到期、出现新的反证或高重要度事件、距上次复核超过 90 天"生成待复核队列，并说明每一条为什么到期；打开后把当初的逻辑原文与交易理由、上次复核之后新增的证据与事件、期间的价格与估值分位、当前持仓盈亏并排展示。复核结论作为逻辑的新版本追加，同时记录当时的价格、PE 分位与盈亏，并把已到期的关联交易复核日期一并推进。季度归因按季统计"仍然成立/受到挑战/已被推翻/维持观察"的分布与当时的盈亏。
- 已实现自动同步与数据健康：行情、日线、公司简况与公告、历史估值、定期报告各自排期运行，可单独开关与改间隔；每个任务有重试、限流、墙钟上限与失败留痕，同一时刻只跑一个任务；“数据状态”页显示每类数据的健康（正常/已过期/有失败/从未成功/已停用）、上次成功时间、下次运行与最近 12 次运行记录，手动“立即运行”始终可用。
- 已接入历史估值与分位：百度股市通近五年的市盈率（TTM）与市净率序列落到本地，公司档案新增“估值分位”区，给出当前值、近 3 年与近 5 年分位、样本量、样本区间、最低/中位/最高，以及带 25%–75% 区间和中位数的历史曲线。样本不足时只说明原因，不给一个看起来能用的数字；每次同步实时行情还会顺带留一条当日估值快照，逐步积累口径一致的自建序列。
- 已接入待核验收件箱：已同步的公告、分红与解禁进入“待办复核”的收件箱，可按 30/90 天或全部筛选，一键归档为证据或事件（带原文链接与披露日期，可关联投资逻辑、选择支持/反证或重要程度），也可以忽略或退回。归档与否由用户决定，系统不会自动认定某条公告影响了投资逻辑。
- 已实现研究记录的版本与备份：投资逻辑与交易理由的每次修改都追加版本（记录改了哪些字段、改动说明和完整快照），旧版本可在卡片里展开回看；新增“备份与恢复”页，可整库备份、下载、导出手写记录 JSON，以及带条目数校验的恢复（恢复前自动为当前数据留一份安全备份）。数据库结构版本记在 `PRAGMA user_version`，恢复时会拒绝比程序更新的备份。
- 可浏览决策总览、待办复核和公司档案；点击公司、逻辑或事件可进入相应公司档案。
- 可新建公司，并在本地 SQLite 中保存投资逻辑、证据和事件；逻辑状态与事件状态可以更新。
- 总览的行情卡片和云图只使用本机已经关注的公司，不是全 A 市场，也不是行业云图。

截图中宁德时代的“投资逻辑、证据档案、事件记录”为空是正常的：这些字段没有来自 StockSDK 的事实数据，系统不会用示例文字填充。今天它们需要用户录入；后续要实现的是让公告、财报和资讯自动进入“待核验收件箱”，而不是让系统自动替用户确认投资判断。

### 人工与自动化的边界

| 内容 | 当前 | 目标状态 |
|---|---|---|
| 行情及估值原始值 | StockSDK 手动同步 | 定时同步、来源和截止时间可见 |
| 公司名称与代码 | 初始池自动建立；新建时手填 | 搜索或输入代码后校验并自动补全 |
| 财务定期报告 | AKShare / 新浪财经手动同步 | 扩展 TTM、指标字典、原始响应留档和定时同步 |
| 公告、新闻原文 | 未接入 | 自动采集为待核验事实，附来源与时间 |
| 投资逻辑、反证条件、状态 | 用户录入与确认 | 始终由用户确认；AI 只能给出带引用的草案 |
| 事件的重要性及对逻辑的影响 | 用户录入与确认 | 系统可建议分类，用户最终确认 |

## 2. 对照原始六类目标的完成度

说明：**已实现**代表可在当前界面和 API 中使用；**部分实现**代表有可用底座但范围明显较小；**未实现**代表尚无相应数据、接口或界面。

### 2.1 `daily_stock_analysis` 方向

| 功能 | 状态 | 当前情况 |
|---|---|---|
| 自选股管理 | 已实现 | 分组筛选与调整、排序、软移除与放回、按代码批量导入、研究池导出均已可用。 |
| 持仓记录 | 部分实现 | 已有组合、买卖流水、移动加权成本、浮动与已实现盈亏和集中度；尚无券商导出 CSV 导入、分红送转与拆并股调整。 |
| 分析任务及历史 | 部分实现 | 已有复核队列、复核结论与历次复核记录；尚无研究任务实体与指派。 |
| 公司分析报告 | 未实现 | 尚无报告生成、版本和归档。 |
| 新闻、公告、基本面聚合 | 未实现 | 尚未接入这些数据源。 |
| Markdown 报告展示 | 未实现 | 尚无 Markdown 编辑、渲染和引用机制。 |
| AI 模型配置 | 未实现 | 尚无模型、密钥、提示词或调用记录。 |
| 定时任务、缓存 | 部分实现 | 五类数据各自排期、重试、限流与健康显示；尚无缓存策略与失败告警通知。 |

### 2.6 `DaimsenGogo` 方向

## 3.4 持仓账本的重做（隐私优先）

现在的账本要求录入**数量与价格**，这是最敏感的个人财务数据。产品的核心链路
（公司档案 → 投资逻辑 → 复核）**并不需要知道你持有多少股**，持仓只是让复核能按权重排序、
让简报能说「你持有的那家」。所以默认姿态应该是「只要比例」。

- [x] **交易类型补齐**（2026-08-05）：现在只有 `buy`/`sell`。至少要补**现金分红**（摊薄成本，长期收益被系统性低估）、
      **送股/转增**（股数与成本价都变）、**配股**。分红数据本站已有
      （`company_calendar_events` 的分红事项，同花顺来源，带每股金额与股权登记日），
      可由「分红事项 × 持股数」自动生成流水待确认，不用手录。
      **已实现**：`dividend`（现金分红，单列一栏不混进 realized_pnl——卖出赚的差价与拿着收的现金
      是两种钱，合并之后看不出这笔投资靠什么回报）、`bonus`（送股只加股数不加成本，均价自然摊薄；
      不做这一步的话除权后价格腰斩而成本不动，账面会凭空显示巨亏）、`rights`（配股按买入计）。
      公司档案新增总回报 = 浮动 + 已实现 + 分红，分母用**投入过的本金**（只用当前成本，
      卖掉一半后收益率会凭空翻倍）。**老库整表重建**：`shares`/`price` 的 NOT NULL 会挡住分红与送股，
      而 SQLite 不能 ALTER COLUMN——不做这一步，新功能在任何已存在的库上都直接报 IntegrityError。
      账本算术 7 个测试，数字手算过。
- [x] **改为可选 + 只存比例**（2026-08-05）：默认只问「这家占我仓位多少」，不问金额。复核优先级、集中度、
      产业链交叉暴露这些用途只需要比例。**管理员（本人）可开开关保留精确金额**——
      判断归因（「我写下的逻辑，成立的那些是不是真的赚到钱」）是唯一真正需要金额的用途，
      也是本产品最独特的地方。
      **已实现**：`portfolios.amount_mode`（`full` / `ratio`），**新建组合默认 ratio**——
      真实财务状况落在磁盘上该是明确选择而不是默认。已有金额记录的组合改成 ratio 会被挡下：
      留着不显示等于假装没记，要改先删。
- [x] **AI 读截图录入**（2026-08-05）：券商 App 截图 → 模型抽取 → **进待确认队列，绝不自动保存**。
      读错一位数，后面所有成本、浮盈、归因全错且错得隐蔽。截图通常不含手续费，成本价会有偏差，
      界面要说明而不是假装算准了。
      **已实现**：`POST /api/v1/ledger/scan` 收截图（PNG/JPEG/WebP，6MB 内），
      `POST /api/v1/portfolios/{id}/trades/batch` 逐条确认——**一条失败不影响其余**

      账号/姓名/总资产一个字都没漏进结果。截图不落盘。

### 2026-08-05 补：三个只在 PG 上炸的 bug

线上两个定时任务一直失败，查出来全是 SQLite 方言漏进 PG 路径：

1. `INSERT OR REPLACE`（index_members）→ 「全市场底座」整个作业挂掉，
   页面上只表现为云图没数据。改 `ON CONFLICT DO UPDATE`（两边都认）。
2. `row[0]` 在 PG 上是 `KeyError(0)` —— psycopg2 文档明写 RealDictCursor 不支持整数下标，
   而本仓照 sqlite3.Row 写了七处（收件箱整理、今日简报、生成报告都在内）。
   **`KeyError(0)` 的 str() 就是「0」**，于是 last_error 里只留下「inbox_tidy 失败：0」。
   在适配层加整数下标，一处修掉全部七处。
3. `HAVING` 引用 SELECT 别名 —— SQLite 允许，PG 把 `shares` 解析成 `t.shares`，
   报「must appear in the GROUP BY clause」：错在 HAVING，提示却指向 GROUP BY。
   受影响的是今日简报的持仓汇总。

**记到用户头上。** 积分闸口本来就是为模型调用准备的，后台调用不特殊——花的 token

## 2026-08-05：数据隔离改由数据库强制（行级安全）

### 起因

多用户是当天才补的，补在一个「一台机器一份数据」的单机设计上：隔离靠 **101 处
手写的过滤片段**（`_sw` 81 + `_swc` 20），而碰这些表的 SQL 约 93 条。
**漏一处 = 静默泄漏**，测试全绿、页面正常。同一天的审查里就找出 8 处忘了加的，
其中 `PATCH /theses/{id}` 能直接改掉别人的投资逻辑。

靠人记住 101 处等于迟早还会漏，所以把判定挪进数据库。

### 做了什么

27 张表装 RLS 策略，身份靠会话变量 `app.scope` 传（`connect()` 时设一次，本仓
不用连接池，一条连接就是一个 `with connection()` 的生命周期）。

- 12 张自带 `user_id` 的根表：`user_id = app.scope`
- 13 张挂 `companies` 的子表：`company_id IN (SELECT id FROM companies)`
  —— companies 自己也有策略，子查询会被再过滤一次，**等于自动继承归属**，
  省掉一次 14 张表的加列迁移
- `research_task_items`：按 `task_id` 回溯到 `research_tasks`
- `record_revisions`：按 `entity_type` 白名单回溯（不认识的类型一条不给）
- 系统域（`__system__`）看得见全部——调度器要替所有人同步

### 三个踩过的坑

1. **策略装完等于没装。** ENABLE + FORCE 全开，跑出来仍是所有人看到所有数据——
   连库的角色带 `BYPASSRLS`（本地 docker 超级用户、线上 RDS 主账号都带）。
   **从应用侧完全看不出来**：查询照常成功，只是返回了所有人的行。
   → 建专用角色 `xiamimate_stocks`（`scripts/setup_rls_role.py`），并加
   `rls_status()` 自检——它查的是「这个角色会不会绕过」，不是「策略在不在」。

2. **还原备份会把服务弄坏。** 还原走管理员账号（应用角色受 RLS 限制、dump 不到
   全量），而 pg_dump 脚本带 `CREATE SCHEMA`，重建出来的 schema 归执行者所有，
   应用角色连 USAGE 都没有。当时的表现是：服务 active、`/health` 返回 ok，
   **而任何一次真实查询都报权限不足**——因为健康检查只读系统表。
   → 还原后自动交还属主；`/health` 现在真的 `SELECT` 一次 `companies`。

3. **归属键要挑不可空的那个。** `research_task_items` 同时有 `task_id`（NOT NULL）
   和 `company_id`（可空）。按 company_id 写策略后，`NULL IN (...)` 求值为 NULL
   不是 true，「候选清单转研究任务」整个功能被自己的策略挡死。

### 顺带：全面转向 PostgreSQL

`backend()` 默认从 sqlite 改成 postgres，测试默认通道也改成 PG（用一个
**不绕过 RLS** 的测试角色，否则隔离测试全绿而线上真出事）。
`STOCK_TEST_SQLITE=1` 仍可单独验 SQLite 那条路。

改完立刻就有回报：上面第 3 个坑是转成 PG 默认之后第一次跑测试就暴露的，
在 SQLite 上永远测不出来。

SQLite 保留，但只作为**建表结构的定义方式**（`derive_schema_sql()` 在内存库里跑完
整条迁移阶梯再 dump 出 PG 的 DDL，两边结构不会漂），不再是推荐的运行后端。

### 隔离的边界（说清楚，不含糊）

**受数据库强制保护的**：27 张表，跨用户读和写都由 PG 拒绝，与应用层是否记得加
过滤无关。

**不在策略内的 8 张**，都没有用户维度，是设计如此：
`market_universe`、`universe_valuation_history`、`universe_snapshots`、
`index_members`（全市场行情，谁看都一样）、`provider_syncs`、`sync_schedules`、
`sync_runs`（同步作业状态，整实例一份）、`schema_meta`（结构版本）。

**RLS 管不到的**：备份/还原/下载整库、改定时任务——这些作用于整个实例，没有
「只做我那份」的版本，靠 `access.require_owner()` 按人挡（有测试覆盖）。

**前提**：连库角色不带 `BYPASSRLS`。这一条由 `/health` 的 `row_level_security`
字段和启动日志盯着，配错会立刻可见。

### 本地开发环境也要对齐（否则前面这些白做一半）

改完之后发现本地仍连超级用户 `xiamimate`，`rls_status()` 是
`bypasses_rls=True, protected_tables=0` —— **本地行级安全根本没生效**。
那意味着本地写出会泄漏的代码跑起来一切正常，等于又给「上线才发现」留了一条路。

已把本地 `.env` 也改成 `PG_USER=xiamimate_stocks`（`PG_ADMIN_*` 留主账号给备份用），
并跑了一次 `scripts/setup_rls_role.py --schema stocks`。现在本地：

    role=xiamimate_stocks  bypasses_rls=False  protected_tables=27/27  effective=True

**新机器上克隆本仓之后要做的**（写在这里，否则下次又是一台"看起来能跑但没有隔离"的机器）：

1. `docker compose up -d`（本地 PG）
2. `python scripts/setup_rls_role.py --schema stocks --password <随便设>`
3. 把 `PG_USER` / `PG_PASSWORD` 写进 `.env`，`PG_ADMIN_USER` / `PG_ADMIN_PASSWORD` 留主账号
4. 跑一次 `pytest`，`test_rls.py` 的第一条会替你确认隔离真的开着

- 「工业金属典型周期型，PE 低时往往接近景气顶点」
- 「金价是核心驱动而非经营改善，f_score 难起作用」
- 盐湖股份被排除的理由是「钾肥+锂盐双周期叠加，PE 失真严重，margin_of_safety 无法引用」
  —— 这正是「先分类，再定预期」那个方法自己写着的盲区。

**排查过程里被两个假象带偏，都记下来：**

1. 五个策略全部筛出 0 家 → 先怀疑策略太严，再怀疑数据缺失。查出
   `annual_roe`/`annual_gross_margin`/`dividend_yield` 三列全库为空，重新同步补上了。
2. 补上之后**仍然是 0 家**。逐条规则查，单条都能过几百上千只，合起来却是 0；
   最后发现 `run_screen` 返回的键叫 **`candidates` 不是 `rows`**，我读错键名一直拿到空列表。
   一个键名错误，表现成「策略太严」和「数据缺失」两种完全不同的假象，前后查了很久。

第二个假象尤其值得记：**读错键名不会报错，只会得到空结果**，而空结果在选股这个场景里
本身就是一种合法答案。

### 让「本地数据比代码旧」可发现（freshness.py）

一天之内被同一个根因卡了三次（体检说数据不足、策略筛 0 家两次），每次都先怀疑了
错的地方。共同点是**看不出来**：表里 102 期财报、5537 只股票，数量看着很齐全，
缺的是列——而列缺了不报错，只让下游判断悄悄失去依据。

`freshness.check()` 直接数每列填充率，低于 5% 就报，并给出怎么补。阈值留余量是因为
个别行业天然缺某些科目（银行没有营业成本和存货，实测平安、工行 89 期全空）。
数据状态页把它顶在最前面。

有一条测试专门钉「清单里写的列必须真的在表上」——写错列名会让检查静默失效，
而这个模块的全部价值就是别让缺失静默。

### 条带抓出的 bug：半途失败的迁移不能重跑

「实时行情快照」**最近 24 次全部失败**，而列表里完全看不出来。原因是 v32 把
`market_snapshots` 改按 symbol 存时，`company_id` 那列没删掉、还是 NOT NULL。

根子是迁移守卫的判据错了：写成「**有 symbol 就当已迁移完**」。而第一次跑到这张表
时在删列那步失败了（RLS 策略还引用着它）——symbol 已加上、company_id 还在，
重跑时整张表被跳过。

改成按「**还有没有 company_id**」判断，并让每一步都能重跑接上（ADD COLUMN 前先查、
SET NOT NULL 前先回填空串）。修完实测 9/9 家公司行情已更新。

**半途失败的迁移必须能重跑接上**——只写「跑过没有」的标记是不够的，
要判断「实际做完没有」。
